# OFO-guided MCTS 超参数敏感性（正文短版，v2）

## 1. 使用定位

本稿用于论文正文中的 `Hyperparameter sensitivity` 小节，口径相较 `v1` 做了两点更新：

- 不再把结论只建立在单一 `LUMO(D)` 任务上；
- 优先使用**已完成真值评估**的结果来组织正文论证。

当前 `v2` 最适合写成：**主文强调跨任务可复现的总体趋势，附录再用 `LUMO(D)` 作为细粒度单任务案例。**

目前可直接作为正文主证据的任务包括：

- `LUMO(U)`
- `HOMO(D)`

而 `LUMO(D)` 更适合作为附录中的扩展案例，用于补充 `exploration_weight`、`max_depth` 与 `pruning_patience` 的更完整趋势。

## 2. 正文应强调的核心判断

与 `v1` 最大的不同在于，当前结果**更适合支持“方法在合理参数范围内稳定，但最优点具有任务依赖性”**，而不是宣称存在一组在所有任务上都统一最优的超参数。

可直接提炼为三条正文论点：

1. **搜索超参数确实影响最终性能，但方法并不脆弱。** 在 `LUMO(U)` 与 `HOMO(D)` 上，三组主文级 sweep 都能得到稳定可解释的结果，而不是只有单一参数点可用。
2. **最优搜索强度具有任务依赖性。** 更高预算或更强探索并不会在所有任务上都单调更优；不同任务对“激进搜索”的偏好不同。
3. **安全默认值应落在中等工作区间。** 从当前跨任务结果看，`num_simulations = 800`、`exploration_weight` 取 `1.4 ~ 2.0`、`max_branching = 20` 更适合作为正文中的平衡型默认配置表述。

## 3. 正文可保留的关键证据

| 维度 | 跨任务观察 | 论文层面的解释 | 建议写法 |
| --- | --- | --- | --- |
| `num_simulations` | 在 `LUMO(U)` 上，`200 -> 800` 使平均改善值由 `1.1933` 升至 `1.3681`；在 `HOMO(D)` 上，`200 -> 800` 的平均改善从 `-1.5795` 变化到 `-1.5211`，说明收益已接近饱和 | 预算增加的收益**与任务难度相关**：对更难的上升任务更有帮助，对另一类任务则更早进入平台区 | 不写成“预算越大越好”，而写成“中高预算通常足够，额外预算收益具有任务依赖性” |
| `exploration_weight` | `LUMO(U)` 的平均改善在 `2.0` 最强（`1.3681`），但成功率在 `1.4` 最好（`88.64%`）；`HOMO(D)` 则在 `1.0` 上取得最强改善（`-1.5899`）和最高成功率（`94.14%`） | 探索系数主要控制**搜索激进程度与稳定性**，其最优点不是全任务统一的 | 正文宜写成“中等探索最稳健，过弱或过强都可能偏离任务最优工作点” |
| `max_branching` | `LUMO(U)` 上 `8` 分支取得更强改善（`1.5173`），但成功率明显低于 `20`（`72.21%` vs `83.13%`）；`HOMO(D)` 上 `20` 在改善值和成功率上都优于 `8` | 分支宽度控制的是**激进搜索 vs 稳定覆盖**；过窄宽度可能更冒进，但不一定是更稳健的默认设置 | 正文更适合把 `20` 写成安全默认值，而把更小宽度写成“在部分任务上可换取更强改善的激进选项” |

## 4. 可直接写入正文的段落

为评估 `OFO-guided MCTS` 对搜索侧超参数的敏感性，我们基于已完成真值评估的 `LUMO(U)` 与 `HOMO(D)` 结果，对搜索预算、探索系数和分支宽度进行了主文级单因素扫描。结果表明，该方法并不依赖某一组偶然参数，而是在合理参数范围内保持稳定有效；但与此同时，不同任务对搜索强度的偏好并不完全一致。具体而言，在 `LUMO(U)` 上，增大搜索预算能够持续提升平均改善值，例如 `num_simulations` 从 `200` 增加到 `800` 时，平均改善由 `1.1933` 升至 `1.3681`；而在 `HOMO(D)` 上，相同变化仅带来较小波动，说明部分任务在中等预算下已接近收益饱和。探索系数也呈现类似现象：`LUMO(U)` 在更强探索下获得更高改善，但最佳成功率出现在中等探索区间；`HOMO(D)` 则在较小探索系数下取得更强改善和更高成功率。分支宽度实验进一步说明，较小宽度有时可以换取更激进的优化结果，但会损失稳定性；相比之下，中等宽度在不同任务上更适合作为默认配置。总体而言，这些结果支持如下判断：`OFO` 先验与 `MCTS` 搜索之间形成了稳定互补，方法对搜索参数并不脆弱，但正文中更应强调“稳健工作区间”而非“单一全局最优点”。

## 5. 正文中的推荐配置写法

如果正文需要给出一组**跨任务平衡型默认配置**，建议优先写成：

- `num_simulations = 800`
- `exploration_weight = 1.4 ~ 2.0`
- `max_branching = 20`
- `max_depth = 10`
- `pruning_patience = 3`

如果必须写成单点配置，则建议使用较保守的：

- `num_simulations = 800`
- `exploration_weight = 1.4`
- `max_branching = 20`
- `max_depth = 10`
- `pruning_patience = 3`

其理由是：

- `800` 能覆盖当前主文任务上的有效预算区间；
- `1.4` 在 `LUMO(U)` 上给出最高成功率，同时仍处于 `LUMO(D)` 与 `HOMO(D)` 的可接受工作带内；
- `20` 在当前跨任务结果中比更窄分支更稳健；
- `10` 是 `LUMO(D)` 深度实验中的合理折中点；
- `3` 对应保守且稳定的剪枝设置。

## 6. 应如何处理 `LUMO(D)`

`LUMO(D)` 在 `v2` 里不应再承担“唯一正文主证据”的角色，而更适合作为附录中的**完整单任务案例**。其价值主要体现在：

- 展示更强探索在某些任务上如何显著提升改善值；
- 展示更深搜索路径如何带来持续收益，同时牺牲多样性与结构保持；
- 说明 `pruning_patience` 属于次级敏感因素，而非决定性性能来源。

因此，`v2` 的推荐落点是：**正文写跨任务一致性，附录写 `LUMO(D)` 的细节机制。**
